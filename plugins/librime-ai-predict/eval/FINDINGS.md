# 短词推理效果诊断(离线推理实验)

日期:2026-08-13。用 `eval/infer.py` 复刻插件 C++ 推理路径,从真实日志抽取 3531
条 `(窗口, 拼音, 用户实际提交)` 三元组(`eval/testset.jsonl`)做基准。

## 一句话结论

**「短词效果一般」的根因:模型在「单字/单音节高频词」上最弱(30% 错),而这类词恰恰
是输入法自带词库最擅长的。AI 在跟词库抢它抢不过的生意。**

## 关键数据

模型贪心 top-1 精确命中率(当前插件行为):

| 分组 | 命中率 | 样本 |
|---|---|---|
| 提交 1 个汉字 | **81.4%** | 1471 |
| 提交 2 个汉字 | 92.4% | 1875 |
| 提交 3 个汉字 | 84.2% | 171 |
| prompt 3 字母(单音节 sh/zh/ch) | **69.8%** | 506 |
| prompt 4-8 字母(2+ 音节) | 89-93% | — |

- 贪心失败里 **61% 是单字提交**(273/444)。
- 失败案例几乎全是高频功能词的同音字混淆:`shi`→是/时/事/试、`zai`→在/再、
  `de`→的/德、`you`→有/友、`dou`→都/豆、`zhe`→这/者、`na`→那/拿、`ta`→他/它/她、
  `qu`→去/取、`ba`→把/吧、`dao`→到/道…… 这些是词库按词频排第一、模型却猜不中的。

## 解码实验结论

| 策略 | top-1 | top-3 |
|---|---|---|
| 贪心(现状) | **87.3%** | — |
| beam8 + 抑制标点, top-1 | 85.0%(更差) | 93.7% |

- **beam search 的备选几乎全是同一汉字的标点变体**(`去!`/`去?`/`去?！`…),不是真
  同音字;必须用 `suppress_sequences` 抑制标点 token,beam 才去探索真正的汉字备选。
- 即使抑制标点,beam 的 top-1 排名反而比贪心差(length_penalty 扫描 0.6~2.0 都无法
  修复排名)。说明「答案在 top-3(93.7%)」有 ~6pt 理论空间,但重排信号不好找。

## 建议(按优先级)

1. **别让 AI 抢单字生意(立即、低风险)**:有上下文时,单音节 prompt 不触发;或干脆
   抑制「预测结果只有 1 个汉字」的候选,交给词库。直接解决「短词效果一般」。
   → **已落地**:`min_hanzi`(默认 2)按输出抑制单字候选。
2. ~~解码时抑制标点 token~~:**实测对贪心有害,放弃**。抑制标点后模型把标点换成
   `)`、`_`、控制字符等无法被 `StripAllPunctuation` 清理的垃圾(脏输出 1/600 →
   21/600)。贪心不靠 beam 宽度,抑制标点零收益;留待将来 beam search 再用。
3. **多候选/重排(高投入、有上限但不确定)**:top-3 含答案 93.7% vs 贪心 87.3%,
   但需要真正的重排信号(长度匹配 / 词库词频先验),朴素 beam 的 top-1 是负收益。

## 落地结论(2026-08-13)

- C++ 改动:新增 `min_hanzi` 配置(默认 2),`CountHan(display) < min_hanzi` 时不上屏。
  仅此一条,贪心行为不变、单字候选让位给词库。
- 抑制标点 token 未落地(见上,对贪心有害)。
